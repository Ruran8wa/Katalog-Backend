KATALOG BACKEND - BRANCH CHANGE DIGEST

Purpose
-------
This branch makes the event pipeline runnable locally with Docker Compose,
keeps order processing reliable, and makes the consumer easier to extend and
scale.

1. Docker Compose and local infrastructure
-------------------------------------------
- Added one compose.yaml containing:
  - ASP.NET API
  - Separate background consumer
  - SQL Server with the named sqlserver_data volume
  - Azure Service Bus emulator
  - SQL Edge, required by the emulator
  - One-off EF migration service
- API and consumer wait for healthy dependencies. The API and consumer wait
  for the migration service to complete successfully.
- The Service Bus queue is defined in emulator/Config.json and requires
  sessions.
- The emulator has a custom executable healthcheck because its distroless
  image does not contain /bin/sh.
- The emulator's one-hour default message TTL limit is reflected in its
  configuration and documented in README.md.
- The consumer has no fixed container_name, so it can be scaled with:
    docker compose up --scale consumer=3

Why
---
This gives a reproducible local environment without an Azure subscription,
preserves database data across restarts, applies migrations before traffic is
accepted, and supports consumer recovery testing by stopping only the
consumer. Emulator messages remain intentionally volatile across emulator
restarts, and this limitation is documented.

2. Outbox and Service Bus session handling
-------------------------------------------
- OutboxMessage now stores an optional SessionId.
- OrderService sets SessionId to the saved order ID when creating an
  OrderPlacedEvent.
- Added an EF migration named AddOutboxSessionId.
- OutboxPublisherWorker now publishes the stored SessionId directly.
- Removed payload JSON parsing and the GetSessionId helper.
- Publishing fails explicitly when a message has no SessionId instead of
  silently using the outbox message GUID.

Why
---
The producer knows the correct ordering or grouping key. Keeping that key as
outbox metadata means the publisher does not need to understand every event
payload. New event types can choose their own session key without modifying
the publisher, which better follows the Open/Closed Principle and keeps
responsibilities isolated.

3. Consumer concurrency and scaling
-----------------------------------
- MaxConcurrentSessions,
  MaxConcurrentCallsPerSession, and SessionIdleTimeoutSeconds are now
  configurable through AzureServiceBusOptions.
- Configuration is available through appsettings.json, .env, and Compose
  environment variables.
- Defaults remain 1, preserving the previous conservative ordering behavior.
- Invalid zero or negative values are rejected explicitly.
- Service Bus can distribute different sessions across multiple consumer
  instances while preserving ordering within each session.
- Database transactions and order-status checks continue to provide
  idempotent protection during concurrent processing.

Why
---
Hardcoded concurrency limited throughput and prevented safe horizontal
scaling. Configuration allows the deployment to choose throughput based on
load and database capacity, while the defaults avoid changing behavior
unexpectedly.

4. Typed application configuration
----------------------------------
- Added BackgroundServiceOptions.
- Program.cs binds the BackgroundServices configuration section instead of
  reading Consumer:Enabled, OutboxPublisher:Enabled, and legacy environment
  names through magic strings.
- Compose now controls:
    BackgroundServices__ConsumerEnabled
    BackgroundServices__OutboxPublisherEnabled

Why
---
Typed options make configuration discoverable, easier to refactor, and safer
to extend. Program.cs now depends on named properties instead of repeating
string keys.

Validation completed
--------------------
- docker compose config --quiet passes.
- Application Docker image builds successfully.
- EF migration bundle builds successfully.
- Local Compose startup was verified with healthy SQL Server, SQL Edge, and
  Service Bus emulator.
- /health/live and /health/ready returned Healthy.
- Consumer logs confirmed connection to orders-queue and session processing.

Points to mention in the senior check
-------------------------------------
- Session IDs are explicit outbox metadata, not inferred from arbitrary JSON.
- Defaults favor correctness and ordering; concurrency can be increased
  deliberately through deployment configuration.
- Scaling consumers is supported, but database capacity and transaction
  behavior should be load-tested before increasing concurrency in production.
- The emulator is a development/test dependency, not a production broker.
